# 범위 보호: 아키텍처 페이지와 사용 사례 패턴 페이지 비교

블루프린트 사이트는 **아키텍처 다이어그램 페이지**&#x200B;를 **사용 사례 패턴 페이지**&#x200B;와(과) 구분합니다. 이는 서로 다른 판독기의 요구를 충족하기 때문입니다. 이 문서는 경계를 넘어 이동하는 콘텐츠를 처리하는 위치와 방법을 정의합니다.

## 핵심 차이점

- **아키텍처 다이어그램 페이지**&#x200B;는 최상위 수준의 시각적 참조입니다. 그들은 다음과 같이 대답합니다. *&quot;이러한 시스템은 어떻게 서로 맞물립니까? 통합 지점은 어디에 있습니까? 데이터 흐름의 형태는 무엇입니까?&quot;* 독자들은 자기 동향을 파악하기 위해 이곳에 온다.
- **사용 사례 패턴 페이지**&#x200B;는 구현 안내서입니다. 답변은 다음과 같습니다. *&quot;이 기능을 만들려면 어떻게 해야 합니까? 관련된 기능은 무엇입니까? 성공을 측정하는 KPI는 무엇입니까? 구현 옵션은 무엇입니까?&quot;* 독자는 사용 사례가 있어 배송해야 할 때 이곳에 온다.

## 아키텍처 페이지에 속합니다.

| 카테고리 | 예 |
| --- | --- |
| 최상위 아키텍처 | AEP 및 애플리케이션, Experience Cloud Marketeture, 허브 대 에지 토폴로지 개요 다이어그램 |
| 시스템 데이터 흐름 | 실시간 및 배치 수집 경로, 허브와 에지 간의 프로필 동기화, 조회 및 활성화 흐름 |
| 통합 지점 | AEP이 AJO, CJA, Target, Campaign, Marketo, Workfront, SDK 경계, API 표면과 통합되는 경우 |
| 배포 토폴로지 | 웹 SDK과 모바일 SDK 배포, 서버측 전달, 에지 노드 배치 비교 |
| 애플리케이션 아키텍처 | 단일 애플리케이션(AJO, CJA, RTCDP)이 시스템 수준에서 내부적으로 구성되는 방법 |
| 사용 사례 패턴에 대한 포인터 | &quot;이 아키텍처는 링크가 있는 패턴 X, Y, Z&quot;를 지원합니다. 아키텍처 페이지는 해당 콘텐츠를 **복제하지 않음** |

## 아키텍처 페이지에 속하지 않음

다음 중 하나를 작성하는 경우 사용 사례 패턴 페이지로 리디렉션합니다(`use-case-pattern-builder` 스킬 사용).

| 카테고리 | 다른 곳에 속하는 이유 |
| --- | --- |
| KPI 및 측정 공식 | 사용 사례 패턴은 결과를 측정하지만, 아키텍처 페이지는 결과를 측정하지 않음 |
| 비즈니스 목표, 비즈니스 영향 | KBO 콘텐츠는 `/help/blueprints/business-objectives/` 아래에 있습니다. 패턴은 이를 참조합니다. |
| 전술적 사용 사례 예 | &quot;장바구니 포기 알림&quot;, &quot;개인화된 홈페이지 주인공&quot; 등 — 패턴 콘텐츠입니다. |
| 기능(`A > B > C > D`) | 기능 구성은 사용 사례 패턴 템플릿의 일부입니다 |
| 페르소나 내레이션 | &quot;마케터가 원하는 마리아...&quot; 스타일 시나리오는 아키텍처 참조가 아닌 패턴에 속합니다. |
| 구현 옵션 | 다중 옵션 구현 지침(모범 사례, 작동 방법, 장점, 제한 사항)은 패턴 구성입니다 |
| 기본/지원 함수 테이블 | 패턴 페이지 섹션입니다. |
| 사용 사례별 사전 요구 사항 확인 목록 | 패턴은 이러한 요소들을 추적합니다. 아키텍처 페이지는 대신 패턴에 연결됩니다. |

## 다음에 대해 감시할 구문 트리거

새 페이지를 설명할 때 사용자가 다음 구문 중 하나를 제공하면 범위를 일시 중지하고 다시 확인하십시오.

- &quot;KPI&quot;
- &quot;비즈니스 영향&quot; / &quot;비즈니스 결과&quot;
- &quot;전술적 사용 사례&quot; / &quot;예제 시나리오&quot;
- &quot;기능&quot;
- &quot;구현 옵션&quot;
- &quot;최적 대상&quot;
- &quot;장점 및 제한 사항&quot;
- &quot;전제 조건&quot;
- &quot;personas&quot; / &quot;관련자&quot;
- &quot;measurement&quot;

이는 자동으로 페이지의 자격을 박탈하지는 않지만 사용자가 아키텍처 페이지가 아닌 사용 사례 패턴 페이지를 원할 수 있음을 나타냅니다. 생성하기 전에 의도를 확인합니다.

## 콘텐츠가 표류할 때 수행할 작업

1. **드리프트를 식별합니다.** 경계를 넘은 특정 섹션이나 글머리 기호를 가리킵니다.
2. **사용자에게 두 가지 옵션을 제공합니다.**
   - 아키텍처 페이지에서 섹션을 트리밍합니다(가장 일반적임 - 아키텍처 페이지의 포커스를 유지합니다.).
   - 중지한 후 해당 콘텐츠에 대한 `use-case-pattern-builder`(사용자가 실제로 패턴 페이지를 원하는 경우)으로 전환하십시오.
3. **확인을 기다리는 중입니다.** 콘텐츠를 자동으로 다시 작성하거나 삭제하지 마십시오.
4. **아키텍처 전용 콘텐츠를 유지하는 경우** 관련 패턴(기존 또는 만들 대상)에 연결하는 `## Use case patterns supported` 아래의 글머리 기호로 딥콘텐츠를 바꾸십시오.

## Edge 사례

- **페이지가 절반 아키텍처, 절반 패턴입니다.** 아키텍처 페이지(이 스킬), 사용 사례 패턴 페이지(`use-case-pattern-builder` 스킬), 이렇게 두 개의 페이지로 분할합니다. 상호 연결.
- **아키텍처 페이지에서 단일 사용 사례를 전체적으로 설명합니다.** 아키텍처 페이지가 아닌 사용 사례 패턴입니다. `use-case-pattern-builder`(으)로 리디렉션합니다.
- **아키텍처 페이지에 특정 시나리오에 대한 데이터 흐름 예제가 표시되어야 합니다.** 시나리오가 설명적으로만 표시되고 대부분의 페이지가 시스템 아키텍처 수준에 있는 경우 수락할 수 있습니다. 예제를 한 단락에 저장하고 관련 패턴에 연결하여 세부 사항을 확인합니다.

## 빠른 테스트

생성하기 전에 다음 사용자에게 묻습니다. *&quot;독자가 이 페이지에 도달하면 최상위 수준의 아키텍처 참조가 필요합니까? 아니면 절반의 사용 사례 연습이 필요합니까?&quot;* 후자의 경우 페이지는 `use-case-pattern-builder`에 속합니다.
